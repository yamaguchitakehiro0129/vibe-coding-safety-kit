# AIにデータ設計をレビューさせるためのプロンプト

データ構造は、後から変えるのが難しい。
だから、設計の段階で時間をかける価値がある。

このページは、AIにデータ設計をレビューさせるためのプロンプト集である。

---

## ステップ1：エンティティと関係性を言語化させる

いきなりテーブル設計を頼まない。
先に、扱う概念を整理する。

```
これから [サービス名] を作ります。

このサービスで扱うエンティティ（概念）を、洗い出してください。

各エンティティについて、以下を明示してください：
- 名称（日本語と英語）
- 役割
- 主な属性
- ライフサイクル（いつ作成され、いつ消えるか）

そのうえで、エンティティ間の関係を以下の形式で整理してください：
- ユーザーは複数の注文を持つ（1対多）
- 注文には複数の商品が入る（多対多）

```

整理されたエンティティを読んで、抜けがないか確認する。

---

## ステップ2：将来変わる可能性のある箇所を特定させる

設計の段階で、変化への耐性を考える。

```
先ほど整理したエンティティについて、将来的に変わる可能性のある箇所を特定してください。

特に以下の観点でチェックしてください：
1. 今は1対1だが、将来1対多になる可能性のある関係
2. 今は固定の選択肢だが、将来増える可能性のある属性
3. 今は単一の値だが、将来複数の値を持つ可能性のある属性
4. 国際化（多言語対応・通貨対応）の影響を受ける属性

それぞれについて、今すぐ対応する必要があるか、将来の対応で間に合うかを判断してください。
```

---

## ステップ3：削除の方針を決めさせる

物理削除と論理削除のどちらを採るかは、後から変えにくい。

```
このサービスのエンティティについて、削除の方針を提案してください。

各エンティティについて、以下を判断してください：
- 物理削除（レコードを完全に消す）
- 論理削除（削除フラグを立てる、または削除日時を記録する）
- 削除不可（履歴として永続保存する）

判断の根拠：
- 法的に保管義務がある情報か
- 関連するレコードへの影響
- 復元のニーズがあるか
- 個人情報保護の観点で、削除が必要か
```

---

## ステップ4：スキーマを設計させる

ここで初めて、具体的なテーブル設計に入る。

```
これまでの整理に基づいて、データベースのスキーマを設計してください。

各テーブルについて、以下を明示してください：
- テーブル名
- カラム名・型・制約
- 主キー・外部キー・ユニーク制約
- インデックス
- そのテーブル設計を選んだ理由

特に注意すべき観点：
- 第3正規形を基本とする
- 検索条件に使うカラムには、インデックスを設定する
- NULL を許可するかどうかを、明確にする
- タイムスタンプ（created_at / updated_at）を、すべてのテーブルに入れる
- 論理削除を採用するテーブルには、deleted_at カラムを入れる
```

---

## ステップ5：レビューさせる

AIが書いた設計を、別の観点でAI自身にレビューさせる。

```
先ほど設計したスキーマを、以下の観点でレビューしてください。

1. 性能の観点
   - N+1問題が起きそうな箇所
   - インデックスが不足している箇所
   - 大量データになると遅くなる箇所

2. 整合性の観点
   - 外部キー制約の漏れ
   - ユニーク制約の漏れ
   - チェック制約で検証すべき条件

3. セキュリティの観点
   - 個人情報の保存方法
   - パスワードのハッシュ化
   - 暗号化が必要なカラム

4. 拡張性の観点
   - 将来カラム追加が予想される箇所
   - 国際化の影響を受ける箇所

問題があれば、具体的な修正案を提示してください。
```

---

## ステップ6：マイグレーション手順を考えさせる

スキーマ変更をする際は、本番反映までの手順を事前に組む。

```
このスキーマ変更を、本番環境に適用するための手順を組んでください。

考慮すべき観点：
1. ダウンタイムが必要か、無停止で適用できるか
2. 既存データのマイグレーションが必要か
3. ロールバック手順
4. ドライラン（事前検証）の方法
5. 適用後の検証方法（件数確認・サンプル確認）

特に以下のいずれかに該当する場合は、サービス停止を前提に手順を組んでください：
- カラム名の変更
- カラムの型変更
- カラムの削除
- インデックスの再構築

各ステップを、SQLまたはマイグレーションスクリプトとして具体化してください。
```

## ありがちな指摘ポイント

AIに設計をさせると、以下のような問題が頻発する。
レビュー時に、特に気をつけて見る。

* タイムスタンプ（created_at / updated_at）が、一部のテーブルにしかない
* 論理削除と物理削除が、テーブル間で統一されていない
* インデックスが、検索条件のカラムに設定されていない
* 外部キー制約が、設定されていない
* enum的な値を、テキストで持っていて、選択肢が固定でない
* 通貨や数量を、整数ではなく浮動小数点で保存している

---

## 補足：AIに設計させたあとに、必ずやること

* 自分の言葉で、設計を説明できる状態にする
* AIが作った設計図を、自分の手で書き直す（ER図など）
* 想定する操作を、SQLでなぞってみる
* 1万件、100万件のデータが入った時の挙動を、想像する

設計を理解せずに走り出すと、3か月後に作り直しになる。
ここで時間をかける価値は、必ずある。
