# 01. セキュリティ

譲ってはいけない最低線。

---

## まず、考え方から

セキュリティは、機能の一つではない。
最後に追加する装飾でもない。

設計の最初に置いて、最後まで降ろさない前提である。

「あとで対応します」は、ほぼ確実に対応されない。
リリース前に時間がないとき、最初に削られるのがセキュリティだからだ。

だから、最初に置く。
ここを譲ると、ほかを全部やっても意味がない。

---

## チェックリスト

### A. 環境とインフラの選び方

- [ ] AWS / GCP / Azure を生で触っていない
- [ ] PaaS (Vercel / Firebase / Supabase) を使う場合、公開設定を自分の言葉で説明できる
- [ ] SaaS型ビルダー (Lovable / Bolt 等) のデフォルト設定を確認している
- [ ] 「誰がアクセスできるか」を、人に説明できる状態である

なぜか。
IaaSは強力だが、設定の罠が多い。一つ間違えると本番DBが全部抜かれる。
PaaSはマシだが、デフォルトで全公開に近い状態から始まるサービスもある。
最初は、安全側に倒した既定値を提供してくれるサービスから始める。

### B. シークレットと鍵の管理

- [ ] APIキー・秘密鍵をコードに直書きしていない
- [ ] `.env` ファイルを `.gitignore` に追加している
- [ ] 公開鍵と秘密鍵を混同していない
- [ ] 鍵に最小権限しか与えていない
- [ ] テスト用と本番用で鍵を分けている
- [ ] 鍵が漏れたときの再発行手順を確認している
- [ ] エラーログ・スクショ・AIへの質問文に鍵を貼っていない

「SaaSだから安全」の意味は、「秘密の管理を代行してくれる」ではない。
秘密をどこに置き、誰が触れて、漏れたらどう止めるかは、最後まで自分の責任である。

### C. 認可（誰が何を見られるか）

- [ ] ログイン機能と、認可（権限チェック）を分けて考えている
- [ ] URLのIDを変えただけで他人のデータが見えないか確認した
- [ ] データを取り出すたびに、ログイン中のユーザーのものかをサーバー側でチェックしている
- [ ] AIに生成させたAPIコードのレビューをした

「ログインできる」と「他人のデータが見えない」は、別の問題である。

入口の鍵をつけたことと、部屋の中で他人の机を覗けないこと。
この二つを混同すると、IDOR（不正なオブジェクト参照）という典型的な事故が起きる。

### D. 入力の扱い

- [ ] ユーザーの入力をすべて疑って扱っている
- [ ] バリデーションをクライアントだけで終わらせず、サーバー側でも行っている
- [ ] ファイルアップロードの拡張子・サイズ・中身を検証している
- [ ] アップロードされたファイル名を、そのまま保存先パスに使っていない
- [ ] SVG画像を無検証で表示していない

ブラウザのチェックは、UXの補助である。
セキュリティの盾にはならない。開発者ツールを開けば、誰でも数秒で無効化できる。

### E. 依存ライブラリ

- [ ] AIが提案したライブラリを、公式リポジトリで実在確認した
- [ ] 最終更新が直近1年以内である
- [ ] スター数・Issue数・メンテナの活動を確認した
- [ ] ライセンスを確認した（GPL系を商用利用していないか）
- [ ] `package-lock.json` / `requirements.txt` でバージョンを固定している

AIは、存在しないライブラリ名を堂々と提案することがある。
あるいは、5年前にメンテが止まったパッケージを推してくることもある。

依存ライブラリは、外注先である。素性の知れない外注先に、仕事を出さない。

### F. エラーメッセージ

- [ ] 本番環境でスタックトレースを画面に出していない
- [ ] DBのテーブル名・カラム名がエラーに露出していない
- [ ] 「開発モード」と「本番モード」を切り替えている

エラーメッセージは、攻撃者にとっての地図になる。
本番では「処理に失敗しました」程度の抽象的なメッセージだけを返し、詳細はサーバー側のログに残す。

### G. ログと監視

- [ ] アクセスログとエラーログを残している
- [ ] ログの保存先がアプリサーバーだけになっていない
- [ ] 週に一度はログに目を通す習慣がある
- [ ] 異常検知時のアラート設定がある
- [ ] パスワード・APIキー・個人情報をログに出していない

ログは事後にしか役に立たない。
だからこそ、何も起きていないうちから残しておくしかない。

「事件が起きてから記録しておけばよかった」では、手遅れである。

### H. 社内システムだから、という油断

- [ ] 「外部に公開していないから安全」と思っていない
- [ ] 内部からの漏えいリスクを想定している
- [ ] 退職者のアカウントを残していない

漏えいの原因は、外部攻撃より内部の持ち出しやマルウェア感染が多い。
社内ネットワークの「内側＝安全」という前提は、もう成立しない。

### I. 会社のルールとAIツール

- [ ] 会社が承認したAIツール・アカウントだけを使っている
- [ ] 機密コード・顧客データ・APIキーをチャットに貼っていない
- [ ] 会社が利用を許可していないMCPサーバーを業務で使っていない

社外のサーバーに記録が残り続けるリスクを忘れない。
「学習されないから大丈夫」ではない。記録の存在自体がリスクである。

## AIに聞くときの観点

このセクションで扱った概念を、もっと深く知りたいときは、AIに以下のように聞く。

* 「IDORとは何か。具体例とともに、初心者向けに説明して」
* 「Firestore のセキュリティルールでよくある事故パターンを教えて」
* 「私のコードに、入力バリデーションの抜けはないか確認して」
* 「このAPIに、認可チェックは入っているか。コードを読んで指摘して」
