# 02. コスト

寝ている間に、請求は跳ねる。

---

## まず、考え方から

「使ったぶんだけ払う」は、便利な仕組みである。
ただし、使う量を見積もらないと、青天井の請求書が届く。

LLM API、画像生成、データベース、CDN、ストレージ。
どれも、ユーザーが多ければ多いほど請求が増える設計である。

設計を考えずに使い始めると、ある朝、3か月分の家賃が消えている。

---

## チェックリスト

### A. 実装前の見積もり

- [ ] 使うサービスの課金単位を把握している（リクエスト数 / トークン数 / 読み取り回数 / 容量）
- [ ] 単価と無料枠を、公式ドキュメントで確認した
- [ ] 「1日100人が10回使ったら月いくら」を試算した
- [ ] ハードリミット（上限超過で強制停止）を設定できるかを確認した
- [ ] 無料期間終了後の価格を読んでいる

### B. アラートと監視

- [ ] 予算アラートを設定してから、コードを書き始めた
- [ ] 月次予算の50% / 80% / 100% で通知が飛ぶ
- [ ] リリース直後は、毎日請求ダッシュボードを見ている
- [ ] 週次・月次のトレンドを定期的に確認している

「最初に設定したから大丈夫」は、通じない。
使われ方が変われば、コストも変わる。

じわじわ上がっているコストは、日次では気づきにくい。
気づいたときには、月の請求がふくれている。

### C. 設計の罠

- [ ] LLM APIをループの中で叩いていない
- [ ] 1ページの表示で、データベースを数千回叩く設計になっていない
- [ ] 重い処理に、ユーザーのクリック回数の上限を設けている
- [ ] 連打を防ぐ仕組みがある（レート制限・デバウンス）
- [ ] キャッシュできる結果は、キャッシュしている

連打されると課金が増える設計は、悪意あるユーザーに狙われる。
善意の100人より、悪意の1人のほうが、請求書を破壊する。

### D. 環境ごとの分離

- [ ] 開発・ステージング・本番で、課金の発生源を分けている
- [ ] テスト時に本番のAPIキーを使っていない
- [ ] 開発環境で動かしっぱなしのリソースが残っていない

開発環境で深夜まで回り続けるバッチ処理が、月末に数万円の請求になる例は珍しくない。
使っていないリソースは、止める。

---

## ありがちな事故パターン

* LLM APIを無限ループで叩き続けて、一晩で数十万円
* Firestore の読み取り課金を理解せず、トップページで数千回の読み取りが走る設計
* 画像生成APIを「ユーザーが押すたびに」呼び出す設計で、悪意ある連打に遭う
* ベクトルデータベースの保存料金を忘れて、開発中に数万円が積み上がる
* CDNのエッジ転送量を考慮せず、画像最適化なしで配信して帯域料金が爆発する

これらは、すべて「実装前の見積もりを省いた」ことが原因である。
コードを書く前の30分が、月末の数万円を救う。

* 「このサービスの料金体系で、見落としがちな課金ポイントを教えて」
