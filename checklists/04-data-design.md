# 04. データ設計

コードは直せても、データ構造は直せない。

---

## まず、考え方から

ソフトウェア開発で、いちばん変えにくいものはコードではない。
データである。

コードのバグは、書き直せば消える。
データ構造の負債は、後から払うと、利息がついて返ってくる。

ユーザーデータが入った後のテーブル変更は、何もない状態の100倍難しい。
「あとで直そう」が通用しない、唯一の領域だと思っていい。

ここを雑にすると、3か月後の自分が泣く。

---

## チェックリスト

### A. コードを書き始める前に

- [ ] アプリが扱う「エンティティ」を言語化した（ユーザー、注文、商品、など）
- [ ] エンティティ間の関係を整理した（1対多、多対多）
- [ ] 「将来、増えそうな項目」を特定した
- [ ] 「選択肢が固定でないなら、別テーブルにする」を検討した
- [ ] 削除の扱い（物理削除 / 論理削除）を、最初に決めた

AIに「テーブル設計して」と頼む前に、自分の言葉で構造を説明できる状態にする。
構造を理解せずに走り出すと、3か月後に作り直しになる。

### B. AIが作ったテーブル構造のレビュー

- [ ] AIが勝手に作ったテーブルを、放置していない
- [ ] どんなテーブルが、どんな構造で作られているかを把握している
- [ ] 主キー・外部キー・ユニーク制約が、適切に設定されている
- [ ] インデックスが、必要な箇所に設定されている

AIは「動くもの」を素早く出すのは得意である。
ただし「将来変えやすい設計」を優先するとは限らない。

### C. バックアップ

- [ ] 本番DBに自動バックアップを設定している
- [ ] バックアップの保存期間を把握している
- [ ] バックアップから復旧する手順を、一度は試したことがある

「リストアを実際に試したことがない復旧手順は、存在しないのと同じ」である。
バックアップがあるだけでは、安心してはいけない。

### D. マイグレーション（スキーマ変更）

- [ ] スキーマ変更は、ステージング環境で試してから本番に適用している
- [ ] ドライラン（実行前の影響確認）をしている
- [ ] カラム名変更・型変更・カラム削除は、サービス停止のうえで行っている
- [ ] 変更前後で、データの整合性を確認する手段を用意している
- [ ] ロールバック手順を、事前に確認している

「無停止でスキーマ変更」は、熟練者向けの話である。
ユーザーに告知して潔く止め、終わったら再起動する。これが一番リスクが低い。

### E. 本番データの直接操作

- [ ] 本番DBを、コンソールやSQLクライアントで直接触っていない
- [ ] データ操作は、テスト済みのスクリプト経由で行っている
- [ ] 操作前のバックアップを、必ず取っている
- [ ] 操作後の検証手段（件数確認・チェックサム比較など）を準備している

本番データに `UPDATE` や `DELETE` を直接叩くのは、最後の手段である。
それも、バックアップとリストアのリハーサルを終えた後にだけ、許される。

### F. トランザクションと冪等性

- [ ] 複数のデータ更新を伴う処理に、トランザクション境界を設けている
- [ ] 「途中で落ちたら、どうなるか」を考えてある
- [ ] 「同じ処理を2回呼ばれたら、二重に実行されないか」を確認した
- [ ] 決済・在庫・ポイント加算など、二重実行が致命的な処理に冪等性キーを使っている

決済処理を例にする。
「残高を引く」「在庫を減らす」「注文を作る」の3つのうち、2つ目で停電が起きたら何が起きるか。
お金は引かれたのに、商品は届かない。

これを防ぐ概念が、トランザクションと冪等性である。

### G. 個人情報・機密情報の扱い

- [ ] 個人情報を、必要最小限しか保持していない
- [ ] パスワードを、適切なハッシュ関数（bcrypt / Argon2）で保存している
- [ ] クレジットカード情報を、自社DBに保存していない（決済代行を使う）
- [ ] ログに個人情報・APIキー・パスワードが流れていない

「あとで消せばいい」は通じない。
ログに一度残ったデータは、Datadog や Sentry のような外部SaaSにも転送されている。
最初から書かないのが、唯一の正解である。

---

## ありがちな事故パターン

* テーブルにカラムを追加する変更を本番で試し、ロックがかかってサービス停止
* 削除されたユーザーのレコードが、関連テーブルに残り続けて整合性が崩れる
* 同じ注文ボタンの連打で、二重に課金される
* バックアップがあると思っていたら、設定されていなかった
* 開発時に本番DBを直接編集して、ユーザーデータの一部が壊れる

---

## AIに聞くときの観点

* 「私のスキーマを見て、将来変えにくくなりそうな箇所を指摘して」
* 「この処理、途中で落ちたらデータの整合性はどうなるか」
* 「この処理が2回呼ばれたとき、二重実行を防ぐ仕組みは入っているか」
* 「物理削除と論理削除、このサービスではどちらが適切か」
