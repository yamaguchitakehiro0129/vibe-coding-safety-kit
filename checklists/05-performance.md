# 05. 性能

何人まで耐えるかを、知っておく。

---

## まず、考え方から

最初から完璧に作る必要はない。
ユーザーが10人なら、富豪的な実装でいい。

ただし、「いま自分が書いているコードは、何件まで耐える設計か」は、ぼんやりとでも把握しておく。

これだけで、事故の半分は防げる。
ユーザーが1万人になった瞬間、構造の弱さは一気に表面化するからだ。

---

## チェックリスト

### A. データベースのクエリ

- [ ] N+1問題（ループ内でDBを叩く構造）が発生していない
- [ ] 検索が走るカラムに、インデックスが設定されている
- [ ] `SELECT *` を、必要のない場面で使っていない
- [ ] 大量データのクエリに、ページネーションを実装している
- [ ] ページネーションは、件数が増えても劣化しない方式（カーソル型）を検討した

データが100万件を超えると、インデックスのない検索は数十秒かかる。
「動くから大丈夫」では、ユーザー数が増えた瞬間に破綻する。

### B. キャッシュ

- [ ] 同じデータを何度も取得する箇所に、キャッシュを検討した
- [ ] キャッシュの有効期限（TTL）を、適切に設定している
- [ ] キャッシュとDBの不整合が起きたとき、どう復旧するかを考えてある

キャッシュは性能を救うが、整合性の問題を生む。
両者のバランスを意識する。

### C. 外部APIの呼び出し

- [ ] 外部APIを呼ぶ箇所に、タイムアウトを設定している
- [ ] 外部APIが落ちたとき、自分のサービスも止まらない設計になっている
- [ ] レート制限に引っかかったときの挙動を考えてある
- [ ] リトライにバックオフ（再試行間隔の調整）を入れている

外部APIは、必ず落ちる。
落ちる前提で設計するか、落ちてから慌てるかの違いである。

### D. フロントエンド

- [ ] 大きな画像を、最適化せずに配信していない
- [ ] バンドルサイズが、初期表示を妨げていない
- [ ] 不要なライブラリを読み込んでいない
- [ ] Core Web Vitals（LCP / INP / CLS）を一度は測定した

ユーザーは、3秒待たない。
速さは、機能の前にある体験である。

### E. 想定するトラフィック

- [ ] 想定ユーザー数を、明文化している
- [ ] ピーク時のリクエスト数を、見積もっている
- [ ] その負荷で、コストとレスポンスタイムがどうなるかを把握している

「使われるかわからないから見積もらない」は、計画ではない。
仮の数字でいいので、置いてみる。

---

## ありがちな事故パターン

* ユーザー数が10倍になった瞬間、DBのCPUが張り付いてサービス停止
* 画像最適化なしのまま配信して、CDNの転送量料金が爆発
* 外部APIのタイムアウト未設定で、APIが遅いときに自分のサービスも全停止
* キャッシュを入れたが、不整合が起きて古いデータを表示し続ける

---

## AIに聞くときの観点

* 「このクエリ、件数が10万件になったらどれくらい時間がかかるか」
* 「私のコードに、N+1問題が起きていないか確認して」
* 「このAPIに負荷が集中したとき、ボトルネックになりそうな箇所を指摘して」
