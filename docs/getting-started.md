# はじめての人へ

AIにアプリを作らせ始めたばかりの人へ。

---

## このページが扱うこと

このページは、技術用語を最小化した、最初の通り道である。

「動くものができた、誰かに見せたい」と思った瞬間から、
「世に出す前に、何を確認すべきか」までを、最短で渡すための索引である。

全部やる必要はない。
今日のあなたに必要な、3つから5つだけを拾えばいい。

---

## どんな人に向いているか

たとえば、こんな道のりを歩いている人。

* Bolt や Lovable のように、ブラウザだけで動くツールに「こんなアプリが欲しい」と入力して、何かが出てきた人
* Replit でアカウントを作って、数時間で「動くもの」を手にした人
* v0 でフロントエンドを生成し、画面が出てきて感動した人
* Cursor を入れてみたが、何が起きているのかわからないまま、アプリが動いてしまった人
* Claude Code や ChatGPT に頼んで、複数のファイルが生成された人

ツールの名前は変わっていく。
だが、共通しているのは「動いた、けれど、これを世に出していいのかわからない」という地点に立っていること。

このページは、その地点から先の道のりについて書かれている。

## まず、3つだけ

ほかを全部後回しにしてもいいから、これだけはやる。

### 1. シークレットを、コードに直書きしない

APIキー、パスワード、秘密の文字列。
これらをコードの中に書いて、GitHubに上げると、数分で世界中の悪意ある人間に拾われる。

具体的には、

* `.env` ファイルにまとめる
* `.gitignore` に `.env` を追加する
* ブラウザ完結型のツール(Bolt、Lovable、Replit、v0等)を使っている場合、そのツールが用意した「シークレット設定」「環境変数」の欄に入れる

これだけで、最大の事故の一つは防げる。

### 2. 予算アラートを、最初に設定する

クラウドサービス、LLM API、画像生成API。
使ったぶんだけ請求される設計のサービスは、寝ている間に請求が跳ねる。

* 月間予算を決める(迷ったら、月3,000円くらいから)
* 50% / 80% / 100% で通知が来るようにする
* リリースしてから1週間は、毎日請求ダッシュボードを見る

これで、月末に給料が消えている事故を防げる。

### 3. リポジトリは、最初はプライベートにする

GitHubに上げるとき、ほぼ反射的に「Public」を選ぶ人が多い。

最初は、必ず「Private」にする。
誰かに見せる準備ができたら、その時に「Public」に変える。

## 次に、5つ

3つができたら、次にこれをやる。

### 4. 「他人のデータが見えないか」を、確認する

ログイン機能を作ると、人は「セキュリティができた」と勘違いする。
違う。

URLのIDを変えて、他人のデータが見えてしまわないか。
これを、自分のアプリで試してみる。

例:
* 自分のページのURLが `https://myapp.com/orders/12345` だとする
* 別アカウントでログインし直して、URLを `12345` のままにしてアクセスする
* 他人の注文が見えたら、それが事故である

詳しくは [01. セキュリティ](../checklists/01-security.md) のC節を読む。

### 5. 入力は、すべて疑う

ユーザーの入力、外部APIの返り値、アップロードされたファイル。
すべて「悪意ある人間が送ってくるかもしれない」という前提で扱う。

* ブラウザ側のバリデーションは、UXの補助
* 同じチェックを、必ずサーバー側でも行う
* ファイルアップロードは、使っているツールの既定機能を尊重しつつ、サイズと拡張子を確認する

### 6. 「同じボタンを2回押されたら、どうなるか」を、考える

決済、予約、ポイント加算。
2回実行されると致命的な処理は、必ず「2回呼ばれても安全」な設計にする。

AIに頼むときは、こう聞く。
「この処理、2回呼ばれても二重実行されないようにして」

### 7. 本番DBに、自動バックアップを設定する

「あとでやる」が一番危ない。
最初の1日のうちに、設定する。

設定方法は、使っているサービスの公式ドキュメントを見る。
わからなければ、AIに「このサービスで自動バックアップを設定する手順を教えて」と聞く。

### 8. Gitで、こまめに保存する

「昨日まで動いていたのに、今日動かない」を救えるのは、Gitだけである。

* 何かを変えたら、コミットする
* コミットメッセージに「何を変えたか」を書く
* 1日に何度もコミットしていい。多すぎて困ることはない

ブラウザ完結型のツールを使っている場合でも、ほとんどのサービスにはGitHub連携機能がある。
最初に設定しておく。

## やってはいけないこと

ここに書いてあることだけは、やらない。

### コードに直接、APIキーを書く

理由は前述。
AIが「このコードを試してみてください」と提示してきたコードに、APIキーがそのまま埋め込まれていることがある。
レビューせずに動かさない。

### `.env` ファイルを、Gitにコミットする

`.gitignore` に追加するのを、忘れない。
一度コミットしてしまったら、リポジトリの履歴から消すのは難しい。

### 本番のデータベースを、直接いじる

「ちょっと修正するだけ」が、ユーザーデータを壊す。
SQLクライアントで本番DBを直接触るのは、最後の手段である。

### 個人情報をログに出す

メール、住所、電話番号、パスワード、APIキー。
これらをログに出すと、ログの保存先(多くは外部SaaS)にも残る。

最初から、書かない。

### AIに頼んだコードを、レビューせず本番に出す

AIは「動くコード」を作るのは得意だ。
ただし「安全なコード」を作るとは限らない。

最低限、シークレットの直書き、認可の抜け、入力検証の有無は、自分の目で確認する。

### 業法のある領域に、軽い気持ちで踏み込む

医療、金融、法律、教育、不動産、運送、酒類、たばこ、賭博、性風俗、職業紹介。
これらは、法律で許可が必要な領域である。

「相談に乗るアプリ」「お金の使い方をアドバイスするAI」などは、知らずに踏み込んでいることがある。
リリース前に、5分だけ調べる。

詳しくは [03. 法規制](../checklists/03-legal.md) を読む。

## リリース前の最終チェック(最低限)

世に出す日の朝、これだけ確認する。

- [ ] シークレットがコードに残っていない
- [ ] `.gitignore` が機能している
- [ ] 予算アラートが設定されている
- [ ] 自動バックアップが設定されている
- [ ] 利用規約とプライバシーポリシーがある(個人情報を扱う場合)
- [ ] 業法のある領域に踏み込んでいない
- [ ] エラー時に、内部情報が画面に出ない設定になっている
- [ ] URLのIDを変えて、他人のデータが見えないことを確認した

このリストを通過したら、リリースしていい。
