# 中級者向けの索引

個人開発でリリース経験がある人、スタートアップの初期メンバーへ。

---

## このページが扱うこと

このページは、「動かし続ける」ための索引である。

「リリースしたあと、どう運用するか」
「ユーザーが増えたとき、何が壊れるか」
「事故が起きたとき、どう対応するか」

このフェーズで必要になる観点を、深めに整理している。

---

## 中級者にとっての関門

初心者の関門は「動くものを世に出す」だった。
中級者の関門は、別の場所にある。

3つある。

### 一つ。スケールの壁

ユーザー10人と、ユーザー1万人は、別のシステムである。

10人で動いていたコードが、1万人で破綻するのは、構造上の必然だ。
N+1問題、コネクションプール枯渇、キャッシュスタンピード、ホットキー。

これらは、書籍や事例で先回りして学べる領域である。

→ [05. 性能](../checklists/05-performance.md) を起点に、関連する観点を辿る。

### 二つ。データの壁

リリース前のスキーマ変更は、ノーリスクだった。
リリース後のスキーマ変更は、最も難しい技術的作業の一つになる。

* expand-migrate-contract パターン
* 冪等なマイグレーションスクリプト
* ダウンタイムなしの段階的移行

これらは、データが入った後の世界での標準作法である。

→ [04. データ設計](../checklists/04-data-design.md) のD節以降が起点になる。

### 三つ。運用の壁

「動いている」と「監視されている」は、違う。
監視がないシステムは、壊れたことに気づくまで何時間もかかる。

* SLI / SLO / SLA の設計
* ゴールデンシグナル（レイテンシ・トラフィック・エラー・飽和度）
* 構造化ログ・分散トレース

これらは、サービスを長期運用する人だけに必要な知識である。

→ [06. 運用と障害対応](../checklists/06-operations.md) のC節以降が起点になる。

## 中級者向けの追加チェックリスト

各章のチェックリストに加え、この段階では以下を意識する。

### A. アーキテクチャ設計

- [ ] アーキテクチャの選択理由を、文章で説明できる
- [ ] レイヤー分離・責務分担を、コードレベルで実装できている
- [ ] 依存方向が、外側から内側へ統制されている
- [ ] 「なぜこの設計にしたか」をADR（Architecture Decision Record）に残している

### B. ドメインモデリング

- [ ] エンティティ・値オブジェクト・集約の境界を意識している
- [ ] ドメインロジックが、フレームワークから分離されている
- [ ] 「ユビキタス言語」を、コードと会話で一致させている

### C. テスト戦略

- [ ] テストピラミッドの考え方で、テストが配分されている
- [ ] 単体テスト・結合テスト・E2Eテストの役割が、明確に分かれている
- [ ] モックの使いすぎを、避けている
- [ ] 「テストが実装の詳細に依存していない」状態を保てている

### D. CI/CD

- [ ] PRごとに、自動テストが走る
- [ ] mainブランチへのマージで、自動デプロイが走る
- [ ] フィーチャーフラグで、コードのデプロイとリリースを分離できる
- [ ] カナリアリリースまたはBlue-Greenデプロイで、リスクを段階的にする

### E. 可観測性

- [ ] アプリケーションログ・メトリクス・トレースの3本柱が揃っている
- [ ] 構造化ログを使っている
- [ ] SLI（サービスレベル指標）を定義している
- [ ] エラーレートとレイテンシのSLOを設定している

### F. 障害対応

- [ ] オンコール体制が、整理されている（一人運営でも、自分宛のアラート設計はする）
- [ ] ポストモーテムを書く文化がある
- [ ] 「個人のミス」で終わらせず、構造の問題として扱っている

## 観点インデックス

中級者向けに、より深い観点を分野別に並べる。
このリストは、AIに質問するためのキーワードとして使う。

### 設計レビューで見る観点

**A. アーキテクチャ設計**
* レイヤード / ヘキサゴナル / オニオン / クリーンアーキテクチャ
* マイクロサービス vs モノリス vs モジュラーモノリス
* イベント駆動アーキテクチャ（EDA）
* CQRS / イベントソーシング
* BFF（Backend for Frontend）

**B. ドメインモデリング**
* DDD（ドメイン駆動設計）
* 境界づけられたコンテキスト
* ユビキタス言語
* エンティティ / 値オブジェクト / 集約
* ドメインイベント

**C. データ設計**
* 正規化と非正規化のトレードオフ
* イミュータブルデータモデル
* Single Source of Truth
* スタースキーマ / スノーフレークスキーマ

**D. API設計**
* REST原則 / GraphQL / gRPC
* バージョニング戦略
* ページネーション（オフセット型 vs カーソル型）
* 冪等性キーヘッダ
* RFC 7807 Problem Details

**E. 整合性とトランザクション**
* ACID特性
* 楽観ロック vs 悲観ロック
* 分散トランザクション
* Sagaパターン
* 結果整合性
* Outboxパターン

**F. キャッシュ**
* cache-aside / write-through / write-back
* キャッシュスタンピード対策
* TTL jitter
* ホットキー問題

### コードレビューで見る観点

**G. 設計原則**
* SOLID原則
* DRY / KISS / YAGNI
* 関心の分離
* Tell, Don't Ask
* Composition over Inheritance

**H. コード品質**
* 意味のある命名
* 関数の責務分離
* 副作用の最小化
* マジックナンバーの排除
* ガード節と早期リターン

**I. 型設計**
* 型駆動設計
* Make Illegal States Unrepresentable
* 値オブジェクト
* Null安全
* 不変性

**J. テスト**
* テストピラミッド / テスティングトロフィー
* TDD / BDD
* プロパティベーステスト
* コントラクトテスト
* ミューテーションテスト

**K. セキュリティ**
* OWASP Top 10
* OWASP ASVS
* 脅威モデリング（STRIDE）
* ゼロトラスト
* 最小権限の原則

### 運用で見る観点

**L. スケーラビリティ**
* 水平 vs 垂直スケーリング
* ステートレス設計
* シャーディング / レプリケーション
* CAP定理 / PACELC定理

**M. 可用性**
* 単一障害点の排除
* サーキットブレーカー
* バルクヘッド
* 指数バックオフとリトライ
* カナリアリリース / Blue-Green / フィーチャーフラグ

**N. 可観測性**
* ログ / メトリクス / トレース
* OpenTelemetry
* 構造化ログ
* SLI / SLO / SLA
* ゴールデンシグナル

## 使い方

このページの観点インデックスは、目を通すだけで「自分が何を知らないか」がわかる索引である。

知らない用語があれば、AIに以下のように聞く。

* 「○○とは何か。中級エンジニア向けに、具体的なユースケースとともに教えて」
* 「○○と××の違い。それぞれを採用すべき場面の判断基準は」
* 「私のサービスで○○を導入する場合、どこから始めるべきか」

ひとつの用語を起点に、芋づる式に関連概念に触れていく。
これが、中級者の学び方である。
